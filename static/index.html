    BEHIND THE DIAGRAM

    Architecture notes

    A teaching model of a staged, active-active release across two separate OpenShift clusters.

    01

    Independent by design

    OpenShift 4.22 is the requested target. Each datacenter has its own API, etcd, nodes, pod network, GitOps and Rollouts controllers. Service Mesh 3 uses a shared mesh identity and trust root, with one primary istiod per site.

    02

    Three different decisions

    The logical Users → GTM → LTM diagram represents DNS selection. Actual HTTPS connects to the selected LTM VIP, then HAProxy and the mesh gateway. Mesh routing determines local service destinations. “L5 GTM” is interpreted as F5 GTM.

    03

    Local releases, shared services

    Frontend and Orders rollout hosts are cluster-local. Catalog is a shared multicluster service. The mesh uses sidecars, distinct network IDs, reachable API endpoints and dedicated TCP/15443 east-west VIPs on each site's LTM.

    04

    Explicit promotion between sites

    The progressive delivery flow stages A before B. An approved pipeline opens a site-specific Git PR. After merge, that site’s Argo CD auto-syncs. A must be fully healthy on the approved image before a separate B approval and PR. The example uses GitHub Actions protected environments; other CI systems can use the same sequence. Each Rollouts controller manages only its own cluster.

    What the simulation assumes

    Stateless applications, compatible APIs, an independently resilient data tier, sufficient failover capacity, common mesh trust and appropriate network access. Database replication and migrations are outside this demo. All metrics are illustrative; no cluster is contacted.

    YAML is educational, not an installation bundle. Choose exact OpenShift GitOps, Rollouts, Service Mesh and Istio versions against Red Hat's compatibility matrix for OpenShift 4.22. This demo does not assert that every version pairing is supported.

    Certificate rotation uses an external-CA variant

    The identity flow starts with cert-manager and istio-csr already installed in each site, backed by shared Venafi/private PKI and a pinned public root. Workload agents renew through local SDS; private workload keys stay in their pods. ACME is a separate external HTTPS option because cert-manager's ACME issuer cannot sign the SPIFFE URI SANs this mesh requires. Root-CA rollover and migration from the built-in CA require separate plans.
